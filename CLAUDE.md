# Fantasy Land

Dockerized web app. `frontend/` = Vite + React + TypeScript + styled-components + Redux Toolkit (RTK Query). `backend/` = NestJS (TypeScript, ESM). Package manager: **yarn** (never npm/pnpm). Postgres via Drizzle ORM (`db` service in docker compose).

## Running

- `yarn dev` — `docker compose up --build` (frontend http://localhost:5173, backend http://localhost:3000/api)
- `yarn verify` — lint + typecheck + test + build for both apps. Run before calling work done.
- Per app: `yarn fe <script>` / `yarn be <script>` (e.g. `yarn fe add dayjs`, `yarn be test:e2e`)
- After adding a dependency, rebuild and reset the node_modules volume: `docker compose rm -sf backend && docker volume rm fantasy-land_backend_node_modules && docker compose up --build -d` (same for `frontend`). Named volumes are not refreshed by `-V`.

## Frontend conventions (`frontend/src`)

```
api/<endpoint>/        RTK Query: <endpoint>.api.ts (baseApi.injectEndpoints), <endpoint>.types.ts, index.ts
components/<Name>/     shared components
pages/<Name>Page/      one folder per route
store/                 store + typed hooks; slices/<name>/ (<name>.slice.ts, .types.ts, .constants.ts, .selectors.ts, index.ts)
router/                createBrowserRouter + routes.constants.ts (ROUTES)
styles/                theme, GlobalStyle, styled.d.ts (DefaultTheme typing)
test/                  setup + renderWithProviders
hooks/ utils/ types/ constants/   app-wide shared code (create when first needed)
```

Every component/page folder has this shape — create only the files that have content, but never inline them into the `.tsx`:

```
Name/
  index.ts             public exports only
  Name.tsx             JSX + wiring, no styled() calls, no magic strings/numbers
  Name.styles.ts       all styled-components
  Name.types.ts        props & local types
  Name.constants.ts    copy, config, enum-like `as const` objects
  Name.hooks.ts        hooks private to this component/page (app-wide hooks go in src/hooks/)
  Name.test.tsx        tests (vitest + Testing Library)
  components/<Sub>/    sub components, same shape, private to the parent
```

Rules:
- Import via `@/` alias across folders; relative imports only within a component folder. Import other components through their `index.ts`.
- A sub component used by 2+ parents gets promoted to `components/`.
- Styled-components: transient props (`$variant`), theme values only (no raw hex/px in styles except one-offs), types in `.types.ts`.
- `erasableSyntaxOnly` is on: no TS `enum`s — use `as const` objects in `.constants.ts`.
- Server state lives in RTK Query (`api/`), not slices. Slices are for client/UI state. Use `useAppSelector`/`useAppDispatch`.
- Arrow-function named exports (`export const Name = () => …`), no default exports.

## Backend conventions (`backend/src`)

```
main.ts / app.setup.ts   bootstrap; app.setup.ts holds prefix/pipes/filters shared with e2e tests
app.module.ts
config/                  registerAs() configs + config.constants.ts
common/                  cross-cutting filters, guards, interceptors, decorators, pipes
modules/<endpoint>/      one folder per endpoint/resource:
  <endpoint>.module.ts
  <endpoint>.controller.ts
  <endpoint>.service.ts
  <endpoint>.types.ts
  <endpoint>.constants.ts
  <endpoint>.controller.spec.ts / <endpoint>.service.spec.ts
  dto/                   class-validator DTOs (create-<x>.dto.ts, update-<x>.dto.ts, <x>-response.dto.ts)
```

Rules:
- All routes are under `/api` (global prefix). Controller path comes from `<endpoint>.constants.ts`.
- ESM: relative imports end in `.js`. Types-only imports use `import type` (but DI-injected classes must be value imports).
- Controllers are thin; logic lives in services. Validate input with DTOs + the global ValidationPipe.
- Generate modules with `yarn be nest g resource modules/<name> --no-spec` then reshape to the layout above.
- The frontend `api/<endpoint>/` folder mirrors `modules/<endpoint>/`; keep response types in sync.

## Database (Drizzle + Postgres)

- Connection lives in `backend/src/database/` (global `DatabaseModule`). Inject the client with `@Inject(DRIZZLE) db: Database`.
- Tables live beside their feature as `modules/<endpoint>/<name>.schema.ts` and must be re-exported from `database/schema.ts`. Columns use camelCase in TS; `casing: 'snake_case'` maps them to snake_case in SQL.
- Row types go in `<endpoint>.types.ts` via `typeof table.$inferSelect` / `$inferInsert`.
- Migration flow: edit a schema → `yarn be db:generate --name <change>` → commit the SQL in `backend/drizzle/`. Pending migrations run automatically on app boot, under an advisory lock. `yarn be db:studio` opens a browser for the data.
- Unique violations: `getUniqueViolation(error)` from `database/database.utils.ts` returns the constraint name so you can map it to a 409.
- e2e tests (`yarn be test:e2e`) need Postgres running: `docker compose up -d db`.

## Auth

- Cookie sessions: an httpOnly `session` cookie holds a random token, and only its SHA-256 is stored in `sessions`. Sessions last 30 days (`SESSION_TTL_DAYS`) and slide forward once past half their lifetime. Passwords are hashed with argon2id (`@node-rs/argon2`).
- `SessionGuard` is global: **every route requires login unless decorated `@Public()`**. Get the user with `@CurrentUser()`.
- Endpoints: `POST /api/auth/register`, `POST /api/auth/login` (both rate-limited), `POST /api/auth/logout`, `GET /api/auth/me` → `{ user | null }`.
- Frontend: `useCurrentUser()` (`@/hooks`) reads the `getMe` cache. The login, register and logout mutations write the result straight into that cache. Wrap private routes in `<RequireAuth />` and login/register in `<RequireGuest />` (layout routes in `router/index.tsx`).

## Sports data (fantasy picks foundation)

The product's focus is finding the best fantasy picks. Everything sport-specific goes through one pipeline:

```
upstream API → providers/<sport>/ (fetch + map to normalized shapes, cached) → SportsService (score, filter, sort) → /api/sports/*
```

- **Providers** (`backend/src/modules/sports/providers/<sport>/`) implement `SportProvider` from `sports.types.ts`: `getCatalog`, `getStatLines` and `getGameLog`. Each has `<sport>.constants.ts` (stat groups, stat definitions, scoring presets), `<sport>.types.ts` (raw upstream shapes), `<sport>.mapper.ts` (pure mapping, unit-tested) and `<sport>.provider.ts` (HTTP + caching). To add a sport, create a provider and register it in `sports.module.ts`.
  - **MLB**: `statsapi.mlb.com/api/v1` (no key). Pitchers are labeled SP/RP by share of starts. `singles` is derived from hits so points scoring works. Innings are stored as true thirds (`184.2` → 184.667).
  - **NFL**: Sleeper. Documented `api.sleeper.app/v1` (state/players) plus the undocumented `api.sleeper.com` stats/projections endpoints. Sleeper returns far more fields than the offense group defines (50-66 per position) and mapping drops the rest, so the group is where a field gets picked up: air yards (`rec_air_yd`/`pass_air_yd`), red-zone chances, first downs and `tm_off_snp` are carried for the expected-points model, with `adot` and `snap_pct` rebuilt from them. Season stats are **summed from weekly data**, because Sleeper's season totals lag behind in-season; rate stats are rebuilt from `NFL_DERIVED_RATES`. Sleeper asks for fewer than 1000 calls/min and non-commercial use, and that the bulk player list be pulled **at most once a day** — see the player directory below. The **schedule** comes from `api.sleeper.app/schedule/nfl/regular/<season>` — a whole season of fixtures in one ~27KB payload, so a week or a date range is filtered in memory rather than re-fetched. Sleeper publishes no scores at all, so finals come from **ESPN's public scoreboard**, one request per week and only for weeks that already hold a finished game; the two feeds disagree on exactly one abbreviation (`WSH`/`WAS`). A week whose games are all settled is cached as an archived season however live the rest of it still is, or every refresh would re-pull eighteen scoreboards.
  - **Player directory** (`PlayerDirectoryProvider`, another optional capability): the whole league from `players/nfl` in one payload, cached for a day. It is normalized before it is stored — 14.7MB and ~12k entries in, 613KB and 4,386 fantasy-eligible players out (id, name, team, position, group, roster status, shared `availability`, upstream's `search_rank`). It is what `find_player` falls back to for anyone with no stat line yet (rookies, the just-signed, the injured), and what `getGameLog` resolves a player id against, so looking a player up costs one request a day rather than one per player. `matchPlayers` (`sports.utils.ts`) folds accents and punctuation ("jamarr" → Ja'Marr Chase) and orders ties by `search_rank`, because a shared surname should answer with the starter; an exact word beats a longer prefix, or "chase" returns Chasen Hines ahead of Ja'Marr Chase.
- **Scoring**: `scoring/scoring.ts` is sport-agnostic, computing `sum(stat × weight)` with presets per stat group. We never trust upstream fantasy points. NFL presets reproduce Sleeper's own `pts_std/half_ppr/ppr` (≈99% of players match exactly; the rest are rare-play edge cases). `providers/catalog.spec.ts` fails if a rule or default references a stat the group doesn't define; undefined stats are dropped during mapping and would silently score 0.
- **Summary stats** (`summarizePoints`): average, median, stdDev (volatility), floor and ceiling per game. This is the starting point for pick analysis (consistency, trends, matchups).
- **Analysis** (`sports/analysis/`): pure, sport-agnostic engines that `SportsService` composes, in the same spirit as `scoring/`. `matchup.ts` turns team strength into a 0-100 league-relative percentile score plus a grade (metric definitions come from the provider, so the engine stays generic); `form.ts` compares a player's last N games with their season and labels it hot/cold/steady; `starts.ts` projects a pitcher's next starts from their measured rest pattern; `window.ts` slices a game log to an interval (dates, weeks, then `lastN`), `head-to-head.ts` turns those slices into player-vs-player records and two teams' meetings into a series record, and `preview.ts` folds a club's fixtures into a won-lost record and recent results and its players into a team line (only **summable** stats are added up — eleven catch rates summed would look like a team rate and would not be one). A window is a filter over the season game log, not a second fetch, so any interval is free. Head-to-head matches games **by week where the sport has one**, by date otherwise — matching NFL players on date drops a Thursday-vs-Sunday week.
- **Expected points** (`analysis/expected-points.ts`): what a player's *opportunities* were worth, beside what they scored. The engine is handed the opportunity stat keys and the whole league's scored lines, and measures points per opportunity by **weighted ridge least squares through the origin**, one fit per position (a pooled `ALL` model covers positions with too few players). Nothing is hardcoded, so the weights follow the season and the scoring preset they were fit under — a PPR target prices higher than a standard one because PPR players really did score more per target. Guards that matter: no intercept (a player given nothing is expected to score nothing), negative coefficients are dropped and refit (collinear opportunities otherwise price at *minus* two points), and a feature fewer than `minCoverage` of a position's players ever see is left out rather than priced — a fit left to explain QB scoring with trick-play targets valued a QB target at 3.2 points. Measured on 2024: R² 0.90–0.97 per position, Gibbs/Henry/Mayfield top the "outscored the usage" list and Najee Harris/Pickens/Kelce the other end. It is **not** play-by-play xFP: per-game aggregates carry the volume but not each chance's yardline, so touchdown expectation is the soft part (red-zone counts recover much of it). True xFP would mean ingesting nflverse play-by-play and swapping the weight source; the engine takes the weights as input for that reason.
- **Optional provider capabilities** (`sports.types.ts`), narrowest first. `ScheduleProvider` is the fixture list — `getSchedule`, `getHeadToHead` and `getTeamGames` (one club's season, asked for separately because a season-wide slate is 2,400 games in baseball and upstream can narrow it to one club for the same single request). **Both sports implement it.** `LeagueDataProvider` extends it with team strength and roster availability, which only MLB has — its `TeamStrength` is hitting/pitching, so a football provider could not implement it honestly, which is why the two were split. `providesSchedule()` and `providesLeagueData()` make `SportsService` say which of the two is missing rather than failing obscurely, and the schedule view is gated on the narrower one so NFL gets it.
  - A second, smaller optional capability is `OpportunityProvider.opportunityStats` — which stats count as *chances* per stat group, the input the expected-points fit is built from. Only NFL offense has one; a sport or group without it gets a clear "not wired up" rather than a number built from stats its upstream never published.
  - Rosters come from the **40-man**, not `fullRoster` — the latter returns 300+ minor leaguers, and the 40-man still carries 60-day IL players. Statuses are normalized to `AVAILABILITY` (active/injured/minors/inactive) so tools never parse league wording.
  - Games carry a `score` only once they are **final**; a live game's running score is left null so it cannot be counted as a result. `getHeadToHead` asks upstream for just the two teams' meetings rather than filtering a whole season's schedule.
  - MLB publishes probable pitchers only **~4 days out**. Anything past that is projected from rest pattern and every start carries `confidence: 'confirmed' | 'projected'`. The league-wide sweep can only see announced starts, so `getStarts` returns a `coverageNote` saying what it missed; passing `playerIds` measures each pitcher's real rest from their game log.
- **Caching**: `DataCacheService.wrap(key, ttl, loader)` goes memory → Postgres `data_cache` → loader. Concurrent loads are deduped, and it serves stale data if the upstream API fails. Cache the *normalized* result, not raw payloads. Bump `SPORTS_CACHE_VERSION` whenever a mapper/stat definition changes. TTLs: current season 15 min, player directory 1 day, **finished seasons effectively permanent** — their stats cannot change, and the version bump is what invalidates them when *our* mapping does. A week-long TTL there was re-pulling eighteen weekly payloads per stat group to rebuild an identical number.
- **Season warm-up** (`sports.warmup.service.ts`): at boot, in the background, the last `SPORTS_WARMUP_SEASONS` (10) seasons of every sport and stat group are pulled into the cache, along with the player directory. It only pays off because finished seasons never expire — the cost is once per cache, not once per restart — and a season already held is one Postgres read. It is paced by `SPORTS_WARMUP_DELAY_MS` between fetches, never throws, skips a sport whose catalog will not load, and stops on shutdown. `SPORTS_WARMUP=off` disables it; e2e runs set that, since they boot the real `AppModule`.
- **HTTP surface**: `/api/sports/:sport` serves the catalog — including a `capabilities` block (`schedule`, `leagueData`, `expectedPoints`, `playerDirectory`) so a client asks what a sport supports instead of carrying its own list of which sports are wired up for what. Every local dataset has a route beside it: `stats`, `expected-points`, `players` (the directory, paged), `players/:playerId/stats`, `schedule`, `preview`, `starts`, `matchups`, `availability`. These are the same service methods the chat tools call, so anything the model can fetch, the UI can show.
- **Frontend**: `api/sports/` mirrors the DTOs. `/sports/:sport` is a layout route (`SportPage`) that fetches the catalog once and renders `SportTabs` plus an `<Outlet>`; each dataset is a sibling page (`SportStatsPage` is the index, then `SportExpectedPointsPage`, `SportPlayersPage`, `SportSchedulePage`, `SportStartsPage`, `SportMatchupsPage`, `SportAvailabilityPage`) reading the catalog through `useSportContext`. `SportSchedulePage` serves both sports off the `schedule` capability: a sport with weeks gets a week picker and a week column, and the probable-starter columns are dropped where there are none rather than showing two permanent "TBA" columns. A tab whose capability the sport lacks is not rendered at all — a tab leading to "not wired up for this sport" is worse than no tab. Explorer filters live in the URL (`useSearchParamsState`) so views are shareable. The stat columns a user picks live in the `statColumns` slice, persisted to localStorage (`store/persistence.ts`), and are shared by leaderboards and game logs. Format values with `formatStat(value, stat.format)`.

## Chat (local LLM + MCP)

`/api/chat` is a streaming conversation with a local model that answers using live tool data:

```
browser (SSE) ← chat.controller ← ChatService loop → OllamaClient → Ollama (host)
                                          ↓
                                    ToolRegistry
                                    ├─ local tools (in-process) → SportsService → providers
                                    └─ McpService → MCP servers (stdio) → Sleeper API
```

- **Model**: Ollama on the host, reached at `OLLAMA_BASE_URL` (`host.docker.internal` from the container — compose sets `extra_hosts`). `OLLAMA_MODEL` picks the model and it **must support tool calling**. `OLLAMA_THINK=true` streams a reasoning block as separate `thinking` events. `OLLAMA_NUM_CTX` (default 65536) is sent as `num_ctx`: past it Ollama silently drops the oldest messages, so the system prompt and tool schemas have to be paid for explicitly. It is a ceiling, not an allocation — unused context is free, but every 1000 tokens actually sent costs ~2s of prefill, so `MAX_TOOL_RESULT_CHARS` and the row caps, not `num_ctx`, are the real latency dial. Ollama's own `OLLAMA_CONTEXT_LENGTH` clamps it.
- **Warm-up, and why it follows presence.** The first question otherwise pays four cold starts at once — Ollama loading the weights, prefilling the system prompt and tool schemas, spawning the MCP stdio servers and fetching the season catalogs. Measured here, that is **~15s** (2.8s load + ~12s prefilling 5,478 tokens across 21 tools). But residency is not free and cannot be made free: a loaded 9b at q4 holds **~6.9GB** with `num_ctx=65536` (~5.6GB at 8k — the KV cache is a real allocation, whatever its prefill cost), and Ollama has no state where the memory is released but answers stay fast. So warmth is tied to **someone being there**, not to a timer:
  - `OLLAMA_WARMUP=page` (default) loads the model when the chat page opens — `GET /chat/status` calls `ChatService.warmUp()`, and `ChatStatusBar` polls it every `STATUS_POLL_MS` (2 min, `skipPollingIfUnfocused`, which needs the `setupListeners` in `store/`). Boot pays only `prepare()` — the MCP servers and season catalogs, which hold no GPU memory. `boot` also loads the model at startup; `off` leaves the first question to pay.
  - `OLLAMA_KEEP_ALIVE` (default `5m`, `-1` to pin) goes on every request. It only has to cover **absence**, since the page ping covers presence — so closing the tab frees the ~7GB within 5 minutes. Ollama's own default would unload the model *and* the cached prefix mid-session.
  - `warmUp()` sends the **exact prefix a real turn sends** (same system prompt, tools, `think`, options) with `num_predict: 1`. It sends **no user message**, so the cached prefix ends exactly at the system boundary: measured, that makes the first real question prefill in ~0.15s against ~4.6s cold, while a warm-up carrying a dummy question caches a prefix the real one diverges from early and recovers only about half. Note Ollama still reports the **full** `prompt_eval_count` on a cache hit — `prompt_eval_duration` is the only honest signal of reuse.
  - It never throws, is deduped, is skipped mid-conversation (it would queue ahead of the user's own turn) and is rate-limited to `WARM_MIN_INTERVAL_MS`.

- **Loop**: `ChatService.run()` is an async generator yielding `ChatStreamEvent`s. Each round streams one assistant turn; if it produced tool calls they are executed, appended as `role: 'tool'` messages, and the loop runs again — up to `CHAT_MAX_TOOL_ROUNDS`, which stops runaway local models. The controller serializes each event as one SSE `data:` line, and aborts the loop when the client disconnects.
- **Tools** (`modules/tools/`): `ToolRegistry` is the single tool list the model sees. Our own tools are `@Injectable()` classes implementing `FantasyTool` (`definition` + `execute`), listed in `tools.module.ts` and collected through the `FANTASY_TOOLS` token — same multi-provider pattern as `SPORT_PROVIDERS`. They run **in-process**, so they get the real `SportsService`, the Postgres data cache and the scoring engine with no subprocess or second DB pool. Local tools win a name clash with an MCP server's tool (ours shadows Sleeper's weaker `compare_players`). Thrown `HttpException`s become `isError` results carrying the validation message, so the model can correct itself instead of the turn dying. **To add a tool: implement `FantasyTool` under `tools/<area>/` and list it in `tools.module.ts`** — nothing else changes. Tool definitions are already MCP-shaped, so serving them to external MCP clients later is an add-on, not a rewrite.
- **Tool count is a context budget.** Every tool's schema is re-sent on every round, so a near-duplicate is paid for in all of them and gives a small model one more way to choose wrong. Prefer another argument on the tool that already owns the subject to a new entry in `tools.module.ts`. `get_player_stats` (once three tools) and `get_pitcher_starts` (once two) are what that rule produced.
- **Sports tools** (`tools/sports/`): `find_player`, `get_sport_catalog`, `get_leaderboard`, `get_player_stats`, `compare_players` (season or any interval via `startDate`/`endDate`/`weeks`/`lastN`, plus a head-to-head over the games the players shared), `get_schedule` and `get_game_preview`. These are sport-agnostic and take a `sport` argument. Args are coerced through `tools.utils.ts` because small models send numbers as strings and bare strings for arrays. Every list is capped (`LEADERBOARD_LIMIT`, `GAME_LOG_LIMIT`) — an uncapped result will bury the question in the context window. `find_player` searches **every** stat group, not just the first: MLB's first group is hitting, so searching one group would make pitchers invisible.
  - `get_schedule` is every fixture question — what was played and what is coming. It takes **weeks or dates, never both**, because the two would filter each other; a sport without weeks says so rather than ignoring them. An optional `team` narrows it to one club's games. A game carries a `score` only once it is final, so a scoreless row is a game that has not finished.
  - `get_game_preview` sets two teams against one game: the fixture (the next meeting by default, or a `gameId` from `get_schedule`), each side's record, recent results, production and leading scorers, and the series between them. It **absorbed the baseball-only `compare_teams`** — the series record and the interval measuring are still there, and the rest is what made it a preview rather than a history. "Next" is measured against today and not merely against having no score, or a postponed game would be previewed as the next meeting months after it was called off. A sport with team stats supplies the club line and the matchup grades; one without sums its players in the stat group and **says so in `notes`**, since the two are not the same measurement.
  - `get_player_stats` answers one player's season through `include`: `totals` (the default), `games` for the game log, `form` to measure recent games against the season. The three used to be separate tools fetching the same game log and keeping different parts of it. `form` runs the pure `analyzeForm` engine on the log already in hand rather than re-asking the service.
- **Trim the result, not just the schema.** A row's `stats` object repeats its whole group, so results outweigh definitions: 15 MLB hitting rows cost ~1.8k tokens unfiltered and ~1k at the group's `defaultStats`. Every stats tool takes **`stats`** (`resolveStatKeys`/`pickStats` in `tools.utils.ts`) — named keys, validated against the group so a typo is a fixable error rather than a silently missing column. `get_leaderboard` always keeps the key it sorted on, whatever the filter says: a top ten by home runs with no home runs in it is unusable.
- **Stat, group, scoring and sort keys are matched loosely** (`resolveStatKey`/`matchKey` in `sports.utils.ts`): every name a stat already carries — key, `aliases`, abbr, label — is indexed with casing and separators stripped, so "strikeouts", "strike_outs", "K" and "SO" all reach `strikeOuts`. Upstream keys read like `strikeOuts` and `pts_allow_35p`; a model writes the English word, and a round spent recovering from a spelling is a round not spent answering. A name two stats in the group would both claim resolves to nothing rather than to a guess, and an unresolvable one still fails loudly with the valid keys. Add an alias only where key, label and abbr all miss a name the sport actually uses.
- **`ToolContext`** (`execute(args, context?)`) is how one tool serves both callers. A chat turn gets the compact projection — `defaultStats`, ten recent games, matchup score and grade without the per-metric breakdown, and no `consistency.total`/`average` duplicating `fantasyPoints`/`pointsPerGame`. `callLocalToolData` passes `{ full: true }`, so a dashboard still renders every field; same reasoning that already exempts it from truncation. An explicit `stats` argument wins either way.
- **Football tools** (`tools/football/`): `get_expected_points` — the usage-versus-production board, for "is he for real / due to regress / getting unlucky". It fits on the **whole league** and filters afterwards, since pricing a target off one team's players is not pricing it off the league. `delta` is actual minus expected; sorting is restricted to the board's own computed columns for the same reason `get_leaderboard` rejects an unknown sort. Every result carries a one-line `method` note, because a small model that sees "expected points" will otherwise present it as next week's projection. Opportunity counts and the fitted weights ride along only for `full` callers (dashboards) — they are the widest part of a row.
- **Baseball tools** (`tools/baseball/`): `get_pitcher_starts` (every "who is pitching" question — a one-day range for tonight, `confirmedOnly` for announced starts only, `minStarts: 2` for two-start weeks; it absorbed `get_probable_pitchers`, which asked the same service for the same window), `get_matchup_ratings`, `get_player_status`. They default to `mlb` rather than `nfl` and go through the `LeagueDataProvider` capability, so they return a clear "not wired up for this sport" message elsewhere. Date windows are validated and capped by `resolveDateRange` (`sports.utils.ts`).
- **Sleeper tools** (`tools/sleeper/`): `get_user_leagues` shadows the bundled MCP server's version, which defaults the season to a hardcoded past year, so current leagues came back empty and the model blamed the username. Ours defaults to the live NFL season with a one-season fallback, accepts a username wherever an id is asked for, and says which of "no such account" / "no leagues" happened. It also **returns the `user_id`**, having absorbed our `get_user_info`, so the username → user_id → league_id chain is one call. The server's own `get_user_info` is therefore listed in `SLEEPER_DENIED_TOOLS`: with nothing shadowing it, that one — it reads fields off the `200 null` body Sleeper returns for an unknown user and throws an opaque TypeError — would come back into the prompt.
- **MCP** (`modules/mcp/`): `McpService` connects to the servers in `MCP_SERVERS` (JSON; defaults to the bundled `sleeper-mcp` package) over stdio, **lazily on first use**, and flattens their tools into one model-facing list. A server that fails to start is logged and skipped rather than breaking boot or chat. Colliding tool names get namespaced as `<server>_<tool>`, and a server entry may carry `allowTools`/`denyTools` (matched on the name the server itself uses) to keep its surface off the model's prompt — every tool a server offers is paid for in `num_ctx` on every round. The bundled Sleeper server denies `clear_cache` (a chat turn could wipe our cache) and its start/sit, lineup and waiver advice tools, which answer from Sleeper's numbers instead of our scoring engine. Tool output is truncated to `MAX_TOOL_RESULT_CHARS` — local context windows are small. To add a server, append to `MCP_SERVERS`; no code change.
- **Truncation** (`common/text/truncate.ts`): tool results are capped at `MAX_TOOL_RESULT_CHARS`, **structurally** — `serializeToolResult` binary-searches the largest per-list cap that fits, so the model gets valid JSON with fewer rows plus a `_truncated` note saying `<path>: showing N of M`, not a string cut mid-token. MCP text goes through `serializeToolText`, which parses JSON and falls back to character truncation for prose. The system prompt tells the model `_truncated` means "partial but real", because otherwise it reports the truncation as a failure instead of answering.
- **Prompting**: `SYSTEM_PROMPT` in `chat.constants.ts` spells out all three tool families and Sleeper's id lookup chain (username → user_id → league_id), because small models otherwise invent league ids. It also tells the model to pass `sport` explicitly every time and to pass on the confirmed/projected distinction for pitcher starts. `SEASON_CONTEXT` is appended per request with the season (and week, where the sport has one) resolved from **every** catalog: telling the model the year is the only reliable fix for "last season" — instructing it to look the year up does not work at this size. Tune prompts there, not inline.
- **No baseball league connection.** Sleeper covers NFL only, and there is no Yahoo integration, so for baseball the model is told to ask which players are on the user's roster rather than trying to look it up.
- **Publishing our tools** (`modules/mcp-server/`): `POST /api/mcp` serves `ToolRegistry.listLocalTools()` over MCP's Streamable HTTP transport, so Claude Code, Claude Desktop and other agents share this backend's cache and scoring. Note the direction of the two modules: `mcp/` is the **client** we consume third-party servers with, `mcp-server/` is the **server** we expose. It publishes local tools only, via `callLocalTool` — we don't proxy someone else's MCP server. **Stateless** (`sessionIdGenerator: undefined`): a fresh `Server` and transport per request, torn down on response close, so there is no session store and `GET`/`DELETE` are 405. Auth is a bearer token (`MCP_HTTP_TOKEN`) checked in constant time by `McpTokenGuard`, not the session cookie — the callers are agents, not browsers — and the endpoint returns 503 until a token is set. A tool that throws still returns `isError` content rather than a JSON-RPC error, so clients see the reason.
- **Frontend**: `api/streamSse.ts` is a plain `fetch` generator — RTK Query can't model a stream, so only `/chat/status` goes through `baseApi`. `ChatPage.hooks.ts` folds events into turns; tool calls render as expandable rows so you can see what the model actually fetched.

## Dashboards (generated UI)

`/dashboards` is a chat that builds interactive views instead of answering in prose:

```
browser → /api/dashboards/build (SSE) → ChatService.run(options) → model
                                              ↓ build_dashboard tool
                                        DashboardSpec  ──saved as jsonb──→ dashboards table
                                              ↓
browser ← /api/dashboards/run ← DashboardsService → ToolRegistry.callLocalToolData → SportsService
```

- **A dashboard is a spec, never a snapshot.** `DashboardSpec` = `sources` (tool calls) + `widgets`. Opening or refreshing one re-runs its sources, so a saved dashboard is a live view. Besides the spec only the `prompt` column is stored: the words that asked for it, shown above the widgets on `DashboardPage` and appended to (never replaced) on each refinement, so a dashboard carries its own history of what was asked.
- **Prompt budget.** Every widget kind costs tokens in `BUILDER_SYSTEM_PROMPT` *and* the `build_dashboard` schema, on every round, against `OLLAMA_NUM_CTX`. Keep the per-kind wording to a line and the example to one dashboard — what the model most needs that context for is reading a real tool result before it designs.
- **One page builds and edits.** `DashboardBuilderPage` at `/dashboards/create` creates; at `/dashboards/:id/edit` it seeds the preview from the saved dashboard and saves with `PATCH` instead of `POST`. Either way the spec on screen is **sent with every message** (`BuildRequestDto.spec` → `editPreamble`, appended to `BUILDER_SYSTEM_PROMPT`). The chat history carries only the text turns, so without it the model cannot see what it built last round and re-invents the dashboard rather than refining it.
- **The builder gets a longer loop and one second chance.** `BUILDER_MAX_TOOL_ROUNDS` (10, versus the chat's 6) covers the rounds spent on discovery before the first design attempt; a build that runs out leaves the person with nothing, where a chat turn that runs out has still said something. If a pass ends having fetched data but never called `build_dashboard` — a small model answering in prose instead — it gets one `BUILD_NUDGE` retry, and only then the `noSpec` error. **Never let a build end silently**: the panel staying empty while the model's closing sentence claims success is the worst outcome.
- **Building** (`dashboard-builder.service.ts`) reuses the chat loop: `ChatService.run(history, signal, { systemPrompt, extraTools })`. The builder passes `BUILDER_SYSTEM_PROMPT` and one request-scoped tool, `BuildDashboardTool`, which fetches nothing — it validates the model's design and captures it, and the spec goes out as a `dashboard_spec` SSE event alongside the normal chat events. The prompt makes the model **call the data tool first and read the real field names**; designing blind produces columns that render empty.
- **Validation is two passes, and both matter.** `parseSpec` (`dashboards.utils.ts`) checks the shape — ids, references, limits — and is deliberately chatty: every failure names the exact widget, column or id that is wrong, because a `BadRequestException` comes back to the model as a tool error and it fixes it on the next round. It also absorbs small-model quirks (a nested object sent as a JSON string, a missing column `path`, a widget that omits `source` where the spec defines only one, or spells it `sourceId`). Then `reviewSpec` (`dashboards.verify.ts`) runs the spec against the **real tool results** before accepting it, because a structurally perfect spec can still address fields that do not exist — the one failure a person sees as "it fetched, but the widget is empty". A wrong `rowsPath` is repaired in place; a wrong column path comes back naming the fields the rows actually carry. A source that errored or legitimately returned nothing is a note, not a failure: an empty date range is a real, saveable dashboard.
- **A row array is found, not assumed.** Tools name their array for what it holds — `rows` for most, `players` for compare_players and get_player_status, `games` for a game log, `teams` for get_matchup_ratings, `pitchers` for get_pitcher_starts — so `ROW_ARRAY_KEYS` (mirrored in both apps) is searched when `rowsPath` is absent or names nothing. Defaulting to `rows` alone silently rendered the envelope object as one row of dashes.
- **Present but null counts as missing**, in the verifier and the renderer. MLB game rows carry `week: null`, and a chart with `week` on its x axis draws every game at the same empty category.
- **Stat tiles read their object, then the result root.** A KPI row straddles the two — `fantasyPoints` is top-level, `floor` is inside `consistency` — and a widget that could only read one of them was not expressible, which sent the model round the loop rewriting it.
- **Running**: `callLocalToolData` is `callLocalTool` without truncation — a dashboard renders the result rather than feeding it to a context window. Sources run in parallel and failures are per source, so one dead upstream leaves the rest usable.
- **Widgets** are a closed set, rendered by `components/DashboardView/`. Columns address data by **dot path** (`stats.homeRuns`) and are formatted with `formatCell`, so the renderer never knows anything sport-specific:
  - `table` — sortable `DataTable` with optional row ticking. `compare` — the transpose of a table, showing the *ticked* rows side by side. `versus` — the same grid sourced directly from `compare_players`/`get_game_preview`, no ticking, with the better value on each metric marked (a metric says `better: 'lower'` where a smaller number wins, e.g. volatility).
  - `line` / `bar` — one data model, two marks: an `x` axis path plus up to `SPEC_LIMITS.series` series. **A series may name its own `source`**, which is how two players' game logs land on one pair of axes.
  - `stats` — a row of KPI tiles read out of one object (`path: 'consistency'`). `meter` — a 0-100 rating and its grade per row, built for `get_matchup_ratings`. `badges` — status chips per row (availability, hot/cold), matched to a tone in `STATUS_TONES`; unknown wording stays neutral rather than being guessed into a severity.
  - Every widget takes `width: 'full' | 'half'`, laid out in a two-column grid.
  - Each kind has one entry in `WIDGET_PARSERS` (`dashboards.utils.ts`) rather than another branch. **To add a widget kind: add it to `WIDGET_TYPES`, add a parser to `WIDGET_PARSERS`, describe it in `BUILDER_SYSTEM_PROMPT` and the `build_dashboard` schema, render it in `DashboardView`, and add it to the widget guide.**
- **Charts** are drawn with **Observable Plot** in `components/Chart/`, lazy-loaded — Plot pulls in d3 and costs ~90kB gzipped, too much for every page load. Plot is imperative, so the component renders into a ref and measures its own width. The house rules live in `Chart.constants.ts` and `theme.colors.series`: series colors are assigned **by spec position, never by rank**, so a filter can't repaint the survivors; the palette's dark steps are validated against our surface, and only the first three clear the colorblind gates for *every* pair, which is why charts cap at four series and always ship a legend plus direct end-labels. Bars cap at 24px (the band's leftover is air) with a rounded data end, lines get a crosshair whose single tooltip lists every series at that x, and **Show data** prints the same numbers as a table so nothing is gated behind hover. `toNumber` refuses `null`/`''` on purpose: `Number(null)` is 0, and a missed game must not plot as a zero-point game.
- Sorting, ticking and comparing all happen in the browser. The API is hit only on open and on Refresh.
- **Widget guide** (`pages/DashboardExamplesPage`, linked from the dashboards and builder headers): every widget kind described with the words to ask for it, plus an example dashboard that is the real `DashboardView` rendering a real spec against fixed sample data — `DashboardView`'s `sample` prop short-circuits the fetch, so the page documents the widgets themselves rather than a screenshot that drifts.
- `get_leaderboard` rejects a `sort` key its group does not define. It used to fall back to alphabetical order, which reads as a real ranking and quietly made every generated "top N" dashboard wrong.
- The chat pieces are shared, not duplicated: `useChatStream` (any SSE endpoint, plus an `onEvent` hook for extra event types), `ChatComposer` and `MessageBubble` live in `components/`, and `streamSse` is the one SSE reader.
